RevTrace 最新诊断：CPU 算法可行，为什么 GPU 反而变慢？
我已经核查 GitHub 最新提交 528b839，以及 10 月 25 日的两轮 CES V5 实验。

结论：新算法不是没有实现，也不是状态安全出了问题，而是 CPU 模型所优化的预期收益没有在真实双 GPU 执行中兑现。

更重要的是，两轮 GPU 实验反映了不同阶段的问题，不能混为一谈。
阶段	实验规模	实际完成的算法	结论
CES V5 CPU	数学反例、有限 Oracle、运行时回归	行完成分布、批次风险和期限目标；后继规划部分仍独立于在线执行	CPU 模型与安全检查通过
V5 GPU Pilot	48 个在线单元	当前前沿进展规划，尚未完整接入后继期限回传和跨轮服务承诺	性能 NO-GO

因此，不能再把当前失败解释成“算法只实现了一半，等把 CPU 模块接上 GPU 就好了”。这个问题在最新 Closed-loop 版本中已经得到验证。

这不是推倒 RevTrace 的理由，但要求下一轮不再只增加预测特征或搜索深度。

二、找到四个真正需要修改的地方
最新独立诊断让我认为，CPU 与 GPU 的差距并非一个简单的 Bug，而是四项问题叠加。
1. 算法规划自身占用了宝贵的实时期限
这是已经被实际时钟证实的问题。
1.468 s
错峰 Causal 每轮累计规划时间中位数


158 ms
单次规划 P99 中位数


5.08%
规划开销约占实际整轮墙钟比例



在只有 2 秒 Display Deadline 的系统里，一次 158ms 的规划就消耗了约 7.9% 的显示时限。

我还检查到源码中的一个具体问题：

ces_closed_loop.py::_evaluate() 从采样的 now 开始计算预计 GPU 完成时间，而真实 _closed_choose() 还需要完成场景计算、选择 Batch 和 Owner 派发。

也就是说，算法优化的是“从现在立即执行”的计划，但实际上它要先支付一笔不可忽略的决策时间。

在 20 个精确重放快照中，_row_moments 和 _row_probability 合计被大量重复调用；这是一项明确的缓存、向量化与增量计算机会。

但不能把 1.468 秒直接从运行墙钟中减掉当成潜在加速。GPU 可能在其中部分时间仍在忙，具体关键路径需要实测。
2. 当前算法虽然使用行完成分布，却不知道紧期限音频对应哪一条短行
这是更值得提高方法精度的问题。

V5 已经引入 Row-completion CDF，但预测采用同一个 Batch 的历史行时间分布，并使用交换性近似。

CPU 审计有一个很清楚的反例：

相同的一组行完成时间分布，若对应到不同 Deadline 和 Audio Weight，实际及时交付可以是 4 audio-s，也可以只有 2 audio-s。

也就是说，知道“这个 Batch 里有多少短行”还不够。

必须知道：

哪一条带有紧期限的 Session，更可能是能够提前完成的 Row？

这在有不同音频长度、Prompt 长度和 Token 生成行为的 ASR 服务中很重要。

我建议下一版不再只使用共享 Batch CDF，而是建立带请求特征的行完成分布。Direct Generation 的未来输出长度不可提前知道，因此应保留不确定性；Strict Verify 的候选长度已知，可以使用更精确的条件信息。

如果数据不足，就退回保守的共享分布，不允许把模型猜测当作已知 EOS 时间。
3. 实选 Verify 的 Fallback 成本仍然被低估
在最新完整 Closed-loop V5 错峰实验中：
指标	实测
Causal Verify Batch	18 个
预测平均完整占用	0.592 s
实际平均完整占用	0.789 s
预测 Fallback 行	约 11.04
实际 Fallback 行	18

这些是真正被当前 Causal 选中的 Batch，不是同一 Batch 的 Verify/Generate 反事实，因此不能直接推出把其中哪些任务改为 Generate 一定更好。

但预测偏差已经很明确。

这里的新算法不应该继续只用一个 \(\hat p_{\mathrm{reject}}\) 和预计失败行数。

我建议使用：
\[
\Pr(K=k\mid X_B)
\]

其中 \(K\) 是一整个物理 Batch 里实际需要 Fallback 的行数，\(X_B\) 包含当前可观察的批次组成、候选长度、父状态关系和实际执行历史。

随后评估完整的风险敏感占用成本：
\[
C_V(B)=C_{\mathrm{verify}}(B)+C_{\mathrm{fallback}}(B,K)
\]

当训练数据对某一类 Batch 支持不足时，应按风险区间决策，而不是给出很精确、实际却不可靠的点预测。

新的成本模型也必须提供给 Cost-only 强基线，否则不能证明新增因果规划有独立价值。
4. 算法没有完整计入未来 GPU0 工作的长尾影响
这是可能超过前面三个问题的重要系统机制。

最新 72 单元共观察到 8,892 条 Proposer Row，其中 22 条触及生成预算上限。这 22 条 Row 所在的物理 Batch，占全部 Proposer 已付费 Lease 时间的约 20.7%。

这不是说 22 条 Row 独占了 20.7% 的 GPU 时间，更不意味着删除它们就能直接节省这些时间。该指标包含同批其他工作的实际运行。

但它说明：极少数长生成任务可能使整个非抢占式 Batch 长时间不排空。

在错峰 Causal 中，Proposer 累计物理 Lease 中位约 26.680 秒，而 Fine 约 21.207 秒。Causal 虽然减少了部分 Proposer Batch 数量，却没有减少实际计算占用。

目前 GPU1 的 Planner 会展开已释放后继 Authority 工作，却只使用已经派发的 GPU0 Private Job 的剩余完成分布。它没有充分模拟 GPU1 的本次选择如何改变随后尚未派发的 GPU0 请求、真实 Parent、Batch 构成和长尾输出。

所以 CPU 数学模型即使在自己的状态空间里选择了最优计划，也不代表它对真实 GPU 闭环做出了正确选择。

这正是你希望强化的 C2 科学问题：
授权一个未来状态的时机，会反过来改变另一条时间线上后续模型计算的形态与成本。

如果我们能把这一点准确建模并取得独立系统收益，才有机会形成比普通 Verify/Generate 二分类器更强的算法贡献。

三、下一步：我建议做 CES V6，但不再一次性堆叠所有机制
这次的目标是把 V5 中已经证实的性能问题逐项解决，并且明确区分工程加速、成本模型改进和真正的因果调度创新。

暂定研究目标为 Critical-Path-Aware Evidence Scheduling，仍然是 RevTrace 的 C2，不改原论文主题。
V6 的四项具体改动
优先级	算法改进	应修改的核心代码	必须证明的收益
P0	减少规划计算开销：缓存行完成分布、增量更新场景分数、预计算不变工作量	ces_closed_loop.py 的 _evaluate()、_candidate_plans()	在保持相同输入下相同决策的前提下，减少真实 Owner 阻塞时间
P0	测试 Service Guard 是否过度限制选择：保留服务进展，但将性能承诺与认证安全分开	choose_closed_loop()、ClosedLoopState	确定性能退化有多少来自承诺保护，而非实际 GPU 工作
P1	身份感知的 Fallback 与 Row-tail 风险规划	ces_v5_policy.py、校准器	在真实错峰混合 Batch 中避免昂贵的错误 Verify 选择

这里第三、第四项才是需要争取的算法贡献。第一项可能带来实际系统性能收益，但主要属于实现优化。
V6-A：先消除 Planner 的自我阻塞
建议首先在冻结的 V5 实际快照上做语义等价加速。

其要求是：在完全相同的输入快照、校准数据与配置下，优化前后选出的操作、Session、Batch 顺序、预计信用和服务承诺都相同。

我建议把单次规划 P99 从现有约 158ms 下降至 20ms 以内作为工程目标，而不是声称已经可以达到。重点减少 _row_moments() 和 _row_probability() 的重复积分、相同子批的场景重算，以及反复构造共同工作集合的成本。

此外，要把预计规划时间计入可行动作的真实开始时间，而不是每次假定 GPU1 能在观察快照时立即启动。

如果有必要，可以在 GPU1 正在执行上一 Batch 时做只读预规划，Worker 排空后重新检查 Parent、Epoch、Frontier 和实际候选就绪状态，再决定是否采用。预规划绝不能直接获得执行权限。

注意：即使规划成本完全消失，也不意味着能追回错峰 −32% 的 Goodput 差距。 这个优化主要是清除一个明确障碍，为下一项算法提供干净的执行底座。
V6-B：做一次缺失已久的 Service Guard 单因素实验
源码里有一个很值得检验的选择逻辑：
key = (    unpaid_forced,    promise_excess,    promise_tardy,    ...    -finite_prefix_goodput,)



当前算法先比较未服务的强制目标、Promise 违规及迟到程度，之后才比较核心 Goodput 目标。

这不是状态准入安全的必要条件，而是一项调度服务承诺。

它最初用于避免 GPU V5 中同一目标被连续后置 13 次的情况，这个动机成立。但它也可能在负载较重时，使优化器为了保护已经不可兑现的预测承诺，选择 Goodput 更差的计划。

最新 72 单元没有提供同一规划器仅关闭 Service Guard 的 GPU 消融。因此目前无法判断这一优先级规则究竟有多大代价。

我建议直接比较三种控制：原 Hard Guard、保留有限 Aging 的 Soft Guard、以及不使用 Promise 优先级但保留普通防饥饿规则的完整调度器。

三者共用同样的候选、成本模型、预测、准入检查和 GPU 资源。要逐轮检查是否出现无限延期、Commit P99 恶化或者状态安全问题。

如果 Soft Guard 更好，新的学术结论不是“安全保障应该删除”，而是：

认证写权限的安全约束不能与调度器对完成时间的经验预测承诺混成同一级硬优先级。

这可能成为一个有价值的设计原则，但必须通过真实实验验证。
V6-C：对真正被选择的 Batch 建模，而不是对平均 Batch 建模
我认为这项与 V6-B 可以联合形成一次真正的算法升级。

新成本模型需要同时预测两件事：
\[
\Pr(K_{\mathrm{fallback}}=k\mid X_B)
\]

以及
\[
\Pr(T_{r}^{\mathrm{complete}}\le t\mid X_B,r)
\]

前者描述整个 Batch 的实际 Fallback 规模与资源占用；后者描述某条具体 Session Row 能否及时完成。

这样，同一个 Batch 中两个 Deadline 不同的音频任务，即使总计算量相近，也可能产生不同的合法 Goodput。

但要严格处理一个现实问题：Direct Generation 的未来输出长度尚未确定。这里只能根据已知音频长度、真实 Parent、历史 Token 长度和实际 Batch 条件作带不确定性的预测，不能使用事后生成长度作为在线特征。

新的预测器必须同时交给 Cost-only。 如果普通成本调度已经能够使用它取得全部收益，那说明主要贡献来自更好的执行代价模型，而不是新的状态因果算法。
V6-D：最后再尝试两条 GPU 时间线的真实联合调度
只有前三项修复后，仍然观察到明确的 GPU0 尾部阻塞机会，才继续推进这一项。

我不建议再做简单的 Deadline 排序，因为现有代码中 16 个单飞会话和 16 行 Batch 上限经常让整个 Ready Set 一次进入 Batch，排序没有实际改变派发集合。

真正要改变的是合法的子批划分与派发工作量。

例如，依据当前已知 Audio/Prompt、过往输出长度与模型调用成本，形成可测的同构子批，避免少数长行拖住大量紧期限 Row。必须完整计入增加的 GPU 调用、不同 Batch 输入实现、可能改变的 Canonical History 和 CPU 开销。

这部分值得研究，但不能因为 22 条触顶 Row 所在 Batch 消耗 20.7% 的累计 Lease，就把 20.7% 当作可直接回收的收益。

若实际 GPU0 子批没有可靠净收益，这条路线就不扩大；保留此前的物理尾部发现即可。

在错峰到达（Staggered Mixed-F2）下，Causal 在 GPU0 上派发的 Proposer 批次数其实比 Fine 更少（中位数 15 批 vs. 21 批），但 Causal 的 GPU0 累计完整租约（Lease）耗时却比 Fine 长了 25.81%（26.680 s vs. 21.207 s），且单批最长 Proposer 耗时从 Fine 的 2.389 s 暴涨到了 14.548 s（整整 6.09 倍！），并出现了 22/8892 条 Proposer 生成触及 256-token 预算上限（Causal 三次运行中有 2 条触顶，而 Fine 为 0 条触顶）！   物理机理是什么？
在 CPU 数学模型（MATH_REVIEW.md 第 2、5、6 节）中，如果某个前驱任务 $p$ 自身的 2 秒 Display 期限已经错过（$\text{own\_due}(p)$ 已过期），它的直接双期限信用就被记为 0；除非它身后已经释放了能拿到正信用的后继 $q$，否则规划器会倾向于推迟 $p$ 的认证，优先去拆批执行还能赶上 2 秒期限的其他任务。
这在单设备 CPU 调度模型里是完全正确的。但在双 GPU 自回归系统中：   那些自身 Display 已经超时或处于 F2 故障暴露下的会话，往往正是 GPU0 私有分支（branch_tokens）已经被污染或陷入异常生成的会话！   Fine 采用整批 FIFO 推进，在 4.470 s（C99）内就会迅速完成 GPU1 权威认证并强行将 GPU0 的私有分支 Rebase（清洗重置）回干净的 Canonical 父状态，从而把 GPU0 的单批耗时死死按在 2.389 s 以内（0 触顶）。   而 Causal / Inherit 因为把这类“自身 Display 已过期”的会话在 GPU1 上往后推迟（导致 C99 从 4.470 s 恶化至 7.673–8.397 s），使得 GPU0 在没有收到新 Canonical 父状态的情况下，被迫继续以被污染的旧私有分支为条件派发新窗口，直接诱发了自回归重复退化（跑满 256 tokens，单批锁死 GPU0 达 14.548 s）！正如报告第 5.3 节所指出的，当前 GPU1 的未来展开并未模拟“推迟本次认证将如何改变随后新启动的 GPU0 工作及长尾”。   2. 鸿沟二：CPU 拆批反例假设“耗时线性可加”，而真实 GPU 拆批存在高昂的“双倍启动与排空税”在 MATH_REVIEW.md 第 5 节的 CPU 反例中，假设把 2 行批拆成两个 1 行子批 $G(A) \to G(B)$ 时，总耗时不变甚至更短（如单批 $1.0\text{ s}$ vs. 两个单行各 $0.2\text{ s}$，或 $V(A,B)=0.7\text{ s}$ 拆为 $0.1\text{ s} + 0.6\text{ s}$）。   但在真实 GPU 上，每次调用 三、Fine Anchor：这是我最赞成的主算法修改，但不要把 P80 当成性能保证
过去 CES 的问题是：每轮大量枚举 Verify/Generate、不同 Batch 分区、后继状态与 Private 预测，最后选择模型中分数最高的动作。

现在应该反过来：默认执行最强的 Fine Authority。只有存在足够明确的收益证据，才偏离 Fine。

我建议暂称为 Fine-Anchored Causal Evidence Scheduling。

它仍是 RevTrace 的 CES 主线，而不是另一套系统。
默认动作
\[
A_0=\operatorname{FineGenerate}(R)
\]

其中 \(R\) 是当前所有合法、已释放、可在同一个物理 Batch 内执行的 Authority Target。

默认动作直接使用已有 Fine 快速派发路径，不运行 V5 的完整场景树。
只有三种可考虑的替代
- 对已经就绪且目标执行可严格验证的部分候选进行一次同构 Verify Batch；
- 对确实具有紧迫合法前沿、且拆批收益足够大的小集合优先处理，其余任务继续完整计费；
- 对观测到存在高跨轮工作暴露风险的 Parent，优先完成独立可信 Generation，但必须验证这项优先级的真实价值。
不扩大到任意 \(2^{16}\) 个分区，也不继续多层随机计划搜索。
正式的切换条件
与其采用：
\[
\mathbb E[Q(A)]>\mathbb E[Q(A_0)]
\]

我建议改为针对增量收益做风险敏感比较：
\[
\Delta U(A)=
\bigl[Q(A)-Q(A_0)\bigr]
-\lambda\bigl[W(A)-W(A_0)\bigr]
-\mu\bigl[L(A)-L(A_0)\bigr]
\]

其中 \(Q\) 是合法双期限音频进展，\(W\) 是实际物理工作预测，\(L\) 是期限违约风险。所有动作必须比较同一组已释放义务。

只有当保守估计仍支持 \(\Delta U(A)>0\)，且未引入不可接受的 Commit 尾部风险时，才执行替代动作。

这里可以使用校准分位数或条件风险区间，P80 是一个候选设置，但P80 并非最坏情况上界，也不能保证真实线上不劣于 Fine。

同样，默认 Fine 并不能自动保证获得历史 Fine 的 7.818 Goodput。只要某轮发生 Verify/Generate 切换，后续 Batch、Parent 和实际模型输出就可能改变整条时间线。

因此，我赞成 Fine Anchor，不赞成把它叫作有确定性性能下界的 Dominance Algorithm。
为什么它可能比 V5 好？
它直接针对三个已发生的问题：
- 在候选很少就绪的同步负载下，不为几乎不存在的验证机会反复搜索；
- 在 Verify 容易失败的错峰负载下，减少额外验证和 Fallback；
- 在满载条件下保持原本有效的物理 Batch 摊销，避免无证据地拆成多个小 Batch。
目标是把 CPU 调度开销从约 158ms 的 P99 大幅压低。单次规划 5–10ms 是值得冲击的工程目标，但不是已经验证的数字；是否达到还需要对实际 Owner 路径测量。

不过还有一个创新性风险：如果最终算法退化成“基本永远运行 Fine，偶尔切一次 Verify”，它可能取得不错的性能，却未必构成足够强的 C2 算法贡献。

因此必须与同样使用 Fine Anchor、相同成本模型但没有状态因果特征的简单策略做单因素对照。

四、Fallback 算子：缩 Padding 可以试，Suffix-only 必须单独认证
这部分可能带来真正的 GPU 工作减少，因此值得投资。但不能直接把两项优化都塞进主系统。
优化 A：Selective Fallback 重新裁剪 Padding
我已核对冻结源码。当前执行过程确实是选择失败行之后：
indices = torch.tensor(    fallback_indices, dtype=torch.long, device=device)fallback_data = {    k: v.index_select(0, indices)    for k, v in moved.items()}



index_select(0, ...) 只缩小 Batch 第一维，不重新计算其余维度的有效 Padding 范围。

因此，有一个真实的低层优化机会。

但 Qwen3-ASR 的模型输入不仅包含文本 input_ids 和 attention_mask，也包含音频特征及相应的有效长度。其处理结果还可能依赖物理 Batch 形状。

所以正确做法不是直接从所有张量尾部裁剪到 max(valid_length)。

必须分别检查：
1. 文本 Padding 位于左侧还是右侧，以及裁剪后的位置和 Attention Mask 是否一致。
2. 音频特征 Padding、有效帧数及 Batch 内特征布局。
3. 新布局下的实际 FP32 Greedy Token、EOS、Projection 与旧布局是否一致。
4. 若不一致，是否需要把新布局明确作为另一种 Execution Contract，而不能冒充旧目标的等价执行。
当前 Hugging Face 生成实现也明确区分 Attention Mask、位置处理与 Cache 路径，不能假定裁剪 Padding 是与执行无关的纯 CPU 变换。

优化 B：Suffix-only Fallback
这项建议的数学直觉是对的，但实现难度被低估了。

假设候选 Token 为：
\[
\widetilde Z=(z_1,z_2,\ldots,z_m)
\]

正确目标 Teacher-forced Verification 发现第一次不匹配在第 \(j\) 个 Token。

在相同确定性目标执行语义下，如果之前所有 Token 均通过验证，则：
\[
Z_{\mathrm{accepted}}
=
(z_1,\ldots,z_{j-1},g_j)
\]

其中 \(g_j\) 是 FP32 Verifier 在该位置选择的下一个 Token。

后续确实可以从这一合法前缀继续生成，而不必逻辑上从零重新决定每个前缀 Token。

但当前 Worker 并不自动具备这种可复用状态。

因为现在的 Verify 执行：
model.thinker(    **checked,    use_cache=False,    return_dict=True)



这意味着验证阶段没有提供可直接交给 Fallback 的增量 KV 状态。

把正确前缀简单拼到 input_ids，再调用 generate()，不等于复用已经完成的模型计算。模型可能重新执行整个 Prefill；还必须处理音频输入、Token 位置、Attention Mask、生成预算和 EOS。

更重要的是，当前 FP32 Teacher-forced 路径与原 FP32 Greedy Generation 的实际数值语义，在改变 Batch 形状或缓存实现以后，不能直接假定逐 Token 一致。

这种前缀接受与剩余部分续写，本身也属于已有的 Speculative Decoding / Verified Speculation 技术范畴。ICML 2023 的 Fast Inference from Transformers via Speculative Decoding 和 SOSP 2026 的 LLM-42 都有相关机制。

所以我建议：

先统计真实 Fallback 的首次不匹配位置，再决定值不值得实现 Suffix-only。

如果大部分 F2 候选在第一个或第二个 Token 就失配，能够复用的正确前缀非常短，另做 Cache 管理可能得不偿失。

如果存在大量长的正确前缀，才分别比较 Fresh Fallback、Prefix-recompute Continuation 和经过证明的 KV-preserving Continuation。

不论哪种，必须在实际固定的目标执行条件下与完整 FP32 参考生成核对，不能将输出不一致的快捷路径放进 Canonical State。

这项研究即使成功，也首先是一项可复用的执行算子优化。真正的 RevTrace C2 贡献还需要证明，如何在跨轮反馈状态约束下安全选择并协调这项执行能力。

五、我认为真正值得争取的创新，是“提前认证的跨设备收益”，而不只是更快的 Verify
如果我们只把 V6 做成 Fine Anchor + Padding 裁剪，最终可能得到不错的性能数字，但仍然可能被审稿人认为是已有启发式调度与算子优化的组合。

真正能提高 C2 原创性的，是研究 Authority 何时提交，会如何改变未来尚未启动的 Private 计算。

现有 V5 已经能预测正在执行的 Private Job，却没有充分建模此后尚未派发的 GPU0 工作。

我们可以尝试引入一种新的成本：
\[
\Delta W_{\mathrm{future}}(A)
=
\mathbb E\!\left[
W_{\mathrm{GPU0,future}}\mid A
\right]
-
\mathbb E\!\left[
W_{\mathrm{GPU0,future}}\mid A_0
\right]
\]

这里 \(A_0\) 是 Fine 默认认证动作，\(A\) 是某个可选动作。

关键要求是：
- 只计算认证时序可能改变的未来尚未派发工作。
- 已经在 GPU0 上运行且不可取消的 Batch，不得作为可回收成本。
- 不允许用实际 F2 注入标签或未来 Token 长度作为调度特征。
- 只有受控实验支持某项状态特征能预测额外计算时，才给它成本权重。
如此，V6 就有机会从单 GPU 的 Verify/Generate 选择，升级为真正的跨设备反馈状态依赖调度。

但是否有足够大的可利用空间，必须由前面的认证时序干预实验确定。

六、现在最值得执行的实验顺序
我建议不要一次把全部功能改完再跑 100 多个单元。我们已经经历过 V5 CPU 正确、GPU 失败的教训。

阶段 A：Fast Fine Anchor

将复杂规划器替换为轻量 Fine-anchored 策略，缓存计算并计入规划耗时。先在相同 GPU 快照上检查执行选择和实际 Owner 延迟，再做小规模 GPU 对照。
目标：消除 V5 自身的调度成本




阶段 B：真实 Fallback 算子优化

对旧 Strict/F2 真实失败样本测 Padding 裁剪的数值一致性、模型时间和完整 Lease。并统计首次 Token 失配位置，决定 Suffix-only 是否具有收益空间。
目标：直接减少 FP32 物理工作




阶段 C：Authority 时序与未来 Private 成本因果验证

用随机化的同条件 Authority 延迟对照，测量后续 GPU0 生成长度、Batch Lease、已废弃工作和合法显示进展。若确有显著关系，再开发 Branch-hygiene 优先级。
目标：验证独特的双时间线耦合




阶段 D：集成 V6 并进行强基线 GPU 实验

比较 Fine、Fine+共享算子、简单 Fine-anchor Cost Gate、Fine-anchor+因果风险，以及完整 Standard Safe Async。先用开发数据优化，最终在新来源上冻结确认。
目标：证明独立 C2 机制增量



其中 A 和 B 可以独立推进，不需要等 C 的因果实验。

但不能把 A、B 的普通执行器收益全部算给最终因果算法。这必须通过完整消融区分。
推荐的核心评测指标
维度	我们需要争取的结果
状态安全	原 C1 准入不变量、D1、A/B/C/D、WAL、Consumer 全部保持
主要性能	新独立 Mixed 负载上，相比最强合法基线取得可重复的 Goodput 改善
尾延迟	Display P99、Commit P99 和整轮双 SLO 通过率均完整报告
物理成本	两张 GPU 能耗、完整 Batch Lease、Fallback、CPU/IPC/fsync 全计费
质量	终态 WER/CER、Token/Projection、预算触顶与质量非劣性
创新归因	因果风险项是否明显优于使用相同算子和成本模型的简单 Cost-only

预期可以争取独立 Goodput 提升 5%–10% 以上，或同 Goodput 下明显节能，但不应预设能够实现。

七、从 DSN 审稿角度，不能把四组历史结果全部当作独占创新
这份建议的最后一部分，我同意它希望强化原稿的思路，但不同意“审稿人无法拒绝”这种判断。

有四处需要收紧：
- C1 的 1,200 次 F2 暴露证明真实 GPU 执行输入受到了控制干预，但并非 1,200 次独立自然故障。R3 的 Qwen 6/8 投影恢复与总体 5→21 错词数，也不能证明这六条恢复轨迹各自产生了不可逆损害。
- Audit A 的 0/148是所测输入等价路径的负面结果，不是任何更复杂状态等价方法都无法工作的不可能性定理。
- **Row-complete 的 +53.56%**确实是强工程收益，但完整 Standard Safe Async 也取得了相似改善，不能将通用早交付归为 RevTrace 独占算法。
- C3 的不同 RTO来自不同故障域和起止时钟。Audit B 的 Warm Adoption 仍是有界原型，不能和完整冷重启恢复数字放在同一维度直接排序。
我希望 DSN 最终呈现的仍然是三个贡献：

C1：可信反馈状态准入及其跨轮可靠性意义。

C2：双时间线的因果认证协调，以及经过严格验证的可信认证执行算法。

C3：已认证反馈历史的持久化与实际恢复。

新的 V6 如果成功，重点进入 C2；如果不成功，不能为了论文显得更复杂而把每项工程优化都写成新贡献。
