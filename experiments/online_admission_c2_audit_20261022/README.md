# C2：本轮为何不如 Fine，哪些机制空间值得验证

实验身份：REVTRACE-ONLINE-ADMISSION-20261022；冻结运行时
55cd52dfdbab71298cdb7eae3b0c08c9424020c6。
本报告是既有真实 GPU 记录的事后只读分析，不是新 GPU 实验、不改论文，
也不改变原先四组综合性能 NO-GO 或质量非劣性未建立的判定。

## 一、判断

DGFT 不是整体计算变慢，而是在这批到达受限的短流上，用较少的 Authority
工作换来了较慢的认证前沿；F2 下私有分支不能及时沿新父状态恢复，且物理
batch 的统一完成屏障使一些短行不能及时发布。因此，节省的工作主要兑现为
能耗，而不是本轮 Display2s/Commit8s 的有效 Goodput。

这不是靠改措辞能解决的问题，也不是去掉兼容性检查就能合法解决的问题。
存在值得做小规模机制探针的空间，但目前没有足够证据启动完整新系统或宣称
C2 已升级。更不能把已有 Elastic NO-GO 重新命名后再调参。

## 二、证据和原始日志核对

对72个正式单元的表格逐项哈希校验，分解11,736个共同前沿的 Commit 延迟。
另对 Fine、DGFT、完整 Standard Safe Async 的36次运行重新读取并校验原始
events、worker_records、consumer、sessions、config：5,868个首个合法显示事件
与原审计 Display 数字完全相同，最大差0秒。所有分解逐项相加与原延迟一致。
新模型调用为0；所有原始结果字节保留。

### 1. 输在显示期限，而非原始吞吐

Sync16/F2，各指标均是三次运行中位数：

| 指标 | Fine | DGFT Coarse |
|---|---:|---:|
| 全部音频/到达与排空墙钟 |11.4399|11.5067|
| 双期限达标音频比例 |93.1277%|79.3459%|
| 仅 Display 超时的音频秒 |21.245|63.850|
| 仅 Commit 超时/两者同时超时 |0/0|0/0|
| GPU J/音频秒 |35.9672|31.1091|
| Display P99 |2.4734s|3.9298s|
| Commit P99 |4.7536s|7.0386s|

三次配对 Goodput 差的中位数为−19.84%，不能用两列独立中位数相除替代。
Goodput 等于每次运行的原始音频吞吐乘以达标比例；这三者各自的中位数
不要求代数上恰好相乘。Coarse 的所有未达标前沿在此处都满足 Commit8s。
较低负载 cohort8/F2 也一样：Fine 达标音频比例99.8835%，Coarse88.5925%，
未达标均为显示超时。因此，单纯优化 WAL 或继续降低 Authority 频率不是
这轮主要问题的答案。

### 2. 节约的工作是真实的，但不等于快更多

Sync16/F2，Fine→Coarse：Authority 逻辑任务163→59，物理生成批15→10，
去重后的物理模型调用墙钟19.2222→12.8953s；这是墙钟区间，不是 CUDA
kernel 活跃时间。Proposer 对应调用墙钟16.7766→17.3803s。
两路并行，不能把行任务时间累加成物理 GPU 时间，也不能把两路时间相加
当端到端墙钟。

Coarse 的认证区间为6秒，Fine为2秒：共同前沿等待区间积累的音频加权平均
为1.8568秒、最大4秒，Fine为0。Commit P99 的额外等待有明确来源，并非
突然出现一个新的持久化性能缺陷。Sync16/F2 的 Coarse 整次 WAL owner
墙钟中位数0.2125s，Fine0.3006s；它们也不是可从每条 P99 直接相减的量。

### 3. Canonical 切换后的在途私有任务存在真实失配窗口

一个可完整复查的例子（dgft-sync16-F2-r0，source8463-294825-0013）：

* t=14.220：14秒目标的 Proposer 已在旧父版本1下派发。
* t=14.775：覆盖至12秒的新 Canonical 父版本2提交；Exact-P 连续性检查
  报 boundary-projection-mismatch，旧分支不能合法接入新父。
* t=15.849：旧14秒提案发布，但消费者不能将其作为新父下的合法显示。
* t=16.022：下一次派发才 rebase 到版本2，目标已是16秒。
* t=17.939：该次合法显示才覆盖原14秒前沿，延迟约3.939秒。

这是有实际时钟和消费者拒绝证据的“错过一个显示窗口”，不是抽象的
fork、理论猜测，也不是通过字符串拼接可以修的质量问题。

36次运行中，DGFT 有26个“Canonical 失配已知、旧私有任务仍在途”的暴露，
其中23个在发现时尚未过显示期限，14个同时有至少1秒的后续实际 Authority
空档。这些是重复运行中的暴露，不是26位独立说话人。Sync16/F2 为7/7/1个。
例如上述来源在发现失配时距显示期限仅1.225秒，后续 Authority 实际空档
约1.305秒：空间真实但很紧，不能预设重新生成来得及。

故障生成完成到首次新父版本 Proposer 派发的48个 source-run 观测中位数：
Fine0.5949s、Coarse4.5435s；对应同为16位说话人×3次重复，F2 注入的新
Token 总数均为273。该延迟差是观察及机制线索，不是隔离了所有变量的
因果效应估计。

### 4. 批尾完成屏障压住了短行

冻结 Worker 在整个 model.generate 返回、统一后处理后才设置各行相同的
completed_perf，并一次 results.put；GPUExecutor.poll 也按完整批处理。
在 Coarse Sync16/F2 三次运行中，超时前沿分别33/33/60个，其中29/29/54个
的首个合法显示任务，已在 Token 步数上早于批内最长行结束。

这证明存在“已到 EOS 的短行仍要等批尾”的软件交付屏障。它不证明上述
29/29/54个都可修复：现有日志没有逐行 EOS 墙钟，不能按 Token 数比例
推算节省时间，更不能虚构改善后的 P99/Goodput。Fine 也有同类短行机会，
故该优化必须同样提供给 Fine 和 Standard，而不是只给 DGFT。

## 三、建议的机制路线与优先级

### A. 首选验证：逻辑结果完成与物理批次排空分离

先做小探针，记录实际每行完整 EOS 到达、完整 Render、owner receipt、WAL
完成及消费时间；先证明确有足够早到的完整行，再谈算法。保持物理 batch、
张量布局、精度、生成预算与完整输出语义，不做删 Token、降低精度、KV复用
或凭未完成前缀签发证书。测量插桩本身的开销。

若成立，研究 request-complete 与 batch-drained 两种不同的完成状态：完整
EOS 行可在可信 Render/校验后被 owner 处理；GPU Worker 仍保持忙，直到
物理 batch 真正排空，绝不能因收到一行结果就重复派发覆盖其余在途任务。
Authority 行的准入仍须完整证书、当前父状态、前沿连续性及 WAL 成功后发布。
新 Canonical Parent 提前可用后，下一次 Proposer 才有机会避免在旧父上
启动必被拒绝的工作。不能假定提早完成一定改变后继调度或改善端到端指标。

这不是宣称“Token streaming 是我们的创新”。只有证明其与 DGFT 父状态/
前沿协调的组合带来超出通用早返回的净收益，才考虑升级 C2；否则只算公平
共享的执行器工程改进。

### B. 条件备选：已证明失配后的有界新父显示重建

仅在已提交 Canonical P 与私有边界失配、尚有已释放且未合法显示的前沿、
两个期限尚有预算时，研究一次新的合法生成。优先评估利用现有驻留 FP32
Worker 的实际空档，不增加 GPU，不抢占已运行的认证，不改变正常 Canonical
准入粒度；新结果仅为明确标记的 provisional display，不因 FP32 来源就
跳过准入谓词而写状态。重新生成必须从当前已提交 P 和已释放音频出发。

旧分支 Z 不得经 CPU 重解释冒充新父下生成；在途不可取消的原工作仍计费。
所有重建、IPC、队列、额外能耗和后续认证延迟必须收费；若所需时间大于
实际1秒左右空档，就应 NO-GO。一个看见未来结果或已知故障标签的调度器
不是合法基线或可部署策略。

## 四、正式实现之前的门槛与强基线

1. 第一步只验证每行真实 EOS/Render 早到幅度，以及上述失配空档内的新父
   实际生成成本；不能把本次 CPU 时钟筛查称为 GPU 修复结果。
2. 保留 Fine、DGFT、完整 Standard Safe Async、Score/Strict+最强合法
   Fallback；共同提供相同的早返回执行器。另有纯早返回和普通保守等待/
   知失配再生成的简单规则，防止把通用 streaming 优化冒充 C2。
3. 固定原音频与契约做同输入及重复、合法 FP32 Oracle、Token/终止/P/text
   绑定和 A/B/C/D/WAL 检查；物理 batch 形状或时序发生变化时明示其新操作，
   不声称数值结果自动相同。Canonical History 各自独立合法且质量需重新审计。
4. 先预冻结新机制研究的质量、成本、双时限和 Goodput 判据，再运行结果。
   本轮旧判据一律保留 NO-GO，不事后换阈值追认成功。含干净/故障、同步/
   错峰和独立的混合长度负载，所有未完成请求仍在分母内。
5. 若 Fine 同样获益后仍更优、改善仅来自通用执行器、额外生成抵销能耗，
   或兼容性需要未证明的拼接/旧状态复用，就停止 C2 算法升级。

## 五、本轮决策

**GO：有界测量探针与形式化接口设计。NO-GO：现在就启动完整新机制矩阵，
或宣称已找到可超过 Fine 的算法。**

优先把“完整逻辑结果已好，但被物理批尾拦住”测实；若能更早建立合法父
状态，才验证其对失配窗口的系统性改善。备用重建只有紧窗口真实成本通过
才做。普通调 rho、删除消费者兼容性、降低验证预算、给 DGFT 独享资源，
以及按旧测量拼接新动态输出，均不是本报告接受的补强方法。

C2 当前明确的资产仍是安全的授权率分离、双时间线协调及可测成本前沿；
新的候选能否成为论文创新，应由强基线对照后的净增量决定，而不是命名。
