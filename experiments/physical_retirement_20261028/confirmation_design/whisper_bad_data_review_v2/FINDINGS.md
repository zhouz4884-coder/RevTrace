# Whisper 开发坏数据的独立解释（只读；没有新 ASR）

**当前证据首先指向短音频／累计提示的模型与适配合同退化，不支持把 237.647% WER 归因于 Consumer 拼接、截错音频、单独 FP16 故障或 reserve 容量裁剪。** 首次严重循环发生在未裁剪提示时，真实 FP32 Authority 的神经 Z 已经包含循环。与此同时，当前适配方式与原生 Whisper 处理流程有实质差别，仍需少量付费同输入／重复／整源参照，才能在“底模能力”与“适配合同不合适”之间作最终归因。

这里分析的是旧开发来源，不是 24-speaker 确认池。外层队列没有准备完或上传，更没有启动；源文件、失败结果和 110 格旧冻结计划都未修改。

## 1. 坏结果是真实的，没有口径错误

原始单元：`O/confirmation_dev_v2/dev-whisper-rho1-sync-checked_snapshot-r0`。runner 正常结束且独立执行审计通过；最终可信音频覆盖 100%，没有未完成来源、输入丢失、非法安装或不兼容实际视图。**执行合法性通过不等于识别任务质量通过。** 实际 D99=11.719967 秒、可信视图 P99=12.601546 秒，双期限失败。

对完整最终文本独立重算：**808 个词错误 / 340 个参考词 = 237.6471% WER**，与原报告一致。确定性最小编辑对齐的一种分解为 43 个替换、26 个删除、739 个插入；不同最优路径可能改变分项，但不改变 808 的总数。超过 100% 是大量插入的正常 WER 定义，不是分母被缩小。

## 2. 循环从哪里开始

两个首次词语循环都出现在真实完整 Authority 结果中：

- **sid6 / window7**：实际音频 `[192000,199280]`，仅 **0.455 秒**。此前六窗累计可信文本 194 个字符；实际初始 decoder 为 **48 tokens**，提示裁剪 **0**。新生成 256 tokens，以一段关于 rich relative 的八 token 模式持续重复，未 EOS，直到原预算终止。
- **sid7 / window8**：实际音频 `[224000,256000]`，完整 **2 秒**。实际初始 decoder 为 **56 tokens**，提示裁剪 **0**。新 Z 以八 token 模式重复 “The features of the conventionality.” 32 次，触顶 256。其 window9/10 分别再次产生同样的 256-token 循环；这两次才出现 120/376 token 的 conditioning 裁剪。

因此，短末尾可能是一个触发条件，却不能解释全部实例；第二个循环在完整 2 秒就开始。裁剪发生在循环文本已经进入完整可信历史之后，不能把首次循环归咎于 reserve-generation-tail 修复。

还有三个仅看最终文字容易漏掉的异常：sid1/w9、sid3/w10、sid5/w8 分别生成 **252、253、255 个空格 token 220**，同样触顶 256。实际 CPU tokenizer 已验证 token220 是一个空格；原始 Z 的尾空格被声明的 Render `.strip()` 消去，所以最终显示只留下几个词，但完整解码成本仍真实存在。它们不是短结果或免费终止。

七个 Authority 触顶行合计占 **17.552207 / 24.848636 秒模型阶段（70.64%）**、**1,792 / 2,216 个新 tokens（80.87%）**。Whisper Worker 的变长提示行在同一 lease 内逐行串行执行，因而这些循环也给后续合法行造成实际等待；这与其尾延迟变坏一致。当前只读数据没有隔离其他 Host/队列因素，不能把全部 D99 精确地减去这 17.55 秒。

## 3. 哪些解释已经得到／缺少支持

**实际音频与反馈输入没有出现已观测的错位。** 66 个 Authority 行全部满足：实际区间与 job 起止一致；相邻可信区间连续且不重叠；当前 prompt tokens 等于上一可信结果的 state tokens；完整 decoder 输出以前向 hook 记录的真实 initial decoder IDs 开始；剥去该前缀后的 raw 后缀逐 token 等于 Z；实际 Render 按声明 append 得到完整可信文本；初始长度+256 都没有超过 448 容量。没有 F2 注入。

这排除了本记录里“取错累计音频”“又把完整 decoder prompt 当新输出拼了一次”“Consumer 自己复制一遍可信文本”这些直接解释。它不等于完整 Python/Transformers/CUDA 精化证明，也没有逐 logit finite 记录。

**已存在付费的跨精度同输入控制。** Proposer/Authority 的 66 对对应行全部具有相同 CPU 特征、相同真实 initial decoder IDs 与预算；两者使用 FP16/FP32 的实际 GPU 特征和算术。65 对完整 Z 一样，没有触顶与否的分歧。两个首次词语循环在 FP16 与 FP32 中都是同一个 256-token Z。所以当前证据不支持“只是 FP16 出错”；同精度严格重复仍应补，不能把跨精度对照冒充该重复。

**容量策略修复的是可执行性。** 此单元采用 base.en、English/no-timestamps 前缀 `[50257,50362]`、previous marker50360、最大 decoder448、budget256；这些与实际模型配置匹配。它限制 conditioning view，而完整可信历史保留。首次异常远未达到提示容量；后续裁剪只是带着已经退化的近期文本继续生成。不能由“调用不再超448”推导“流式识别合同质量合适”。

**存在值得隔离的适配差异。** 当前每个不重叠 2 秒片段单独调用 generate，输入形状固定 `[1,80,3000]`，对应短输入被补齐到原生特征窗口；提示来自完整累计文本经 get_prompt_ids。新段常带前导空格，Render 又加入一个分隔空格，因此真实历史在窗边界含双空格；两个首循环时分别有 5/6 处双空格。这个事实不是重复文本的后处理来源，却可能影响未来 decoder 条件。是否触发循环尚未有因果证据，不应未经同输入控制就“清理空格”或换合并规则。

## 4. 与原生 Whisper 的准确关系

base.en 的模型说明给出的典型切块是至多 30 秒，并不意味着 2 秒输入被 API 禁止。当前适配是一个合法但很强的受控流式改造：硬切 2 秒、没有边界音频重叠、累计文本重编码与 append。原生完整转录还包含分段、重复/低置信回退与提示重置等逻辑，不能把当前 Worker 直接称作原生 Whisper 流式算法。[模型说明](https://huggingface.co/openai/whisper-base.en)

原生 OpenAI `transcribe` 提供重复压缩率/低 logprob 的温度回退、静音判定及部分情况下的 prompt reset；文档也说明前文 conditioning 可能导致循环。当前 pinned Transformers4.57.6 的相应阈值默认是 None，而 Worker 只传单次 greedy、256预算、无 timestamps；保存的 generation_config 中也没有这些阈值。七个触顶 raw 解码文本的压缩率为 8.77–21.33，空格循环也很高。因此“直接接受第一份贪心 Z”与原生的防循环处理存在明确区别。这里没有运行回退，不声称加回退已经有效；回退会改变选择合同并产生真实额外成本。[OpenAI 实现](https://github.com/openai/whisper/blob/main/whisper/transcribe.py)，[实际 pinned API 源码](https://github.com/huggingface/transformers/blob/v4.57.6/src/transformers/models/whisper/generation_whisper.py)

## 5. 有依据的最小补证，而不是直接换结果

建议 root 在旧开发源上决定一个很小的、有界诊断，确认池继续保持未用：

1. **严格同输入重复**：重放 sid6/w7 与 sid7/w8 的原实际音频、初始 decoder IDs、FP32、原预算和特征，各两次；再加一个 blank-loop 目标 sid5/w8。保留原 peer/串行布局与完整 token/EOS/budget。现有原 A/P 作为已付费的精度对照，不再以换精度猜测原因。
2. **付费整源能力参照**：对上述三个完整原始来源执行同一 base.en 的完整音频、空 prompt 原生短音频参照，计入所有模型与解码成本。它检验 base.en 在该音频上的能力；它是不同音频/分段合同的诊断参照，不能替代原 2 秒结果，也不是部署性能数字。
3. 仅当1稳定、2明显好，才在相同异常目标上隔离一个原因：正常化的窗边界空格或无历史 conditioning（二选一先做，另一个不同时改）。若要比较原生回退，也必须作为单独、付费、明确的新选择合同。任何修复最终对五臂共享并重新冻结，不能只给主方法开优待。

判定逻辑是：重复不稳定时优先查实际输入/运行机制；原输入稳定循环而整源参照合理时，主要缺口在流式适配合同；整源同样很差时，不能要求系统组合机制弥补该模型/来源上的任务能力。当前证据已经足够暂停把这套 Whisper 适配直接送进 110 格确认，但还不足以宣布“base.en 不行”或某个未经测量的修复有效。

本轮没有新 GPU、ASR、模型权重加载或 source 修改。CPU tokenizer 仅解码已经记录的 Z。原完整坏结果、七个触顶行和所有来源都保留。详细输入、逐窗轨迹、质量分项、已付费精度配对与 installed API 摘录分别在同目录 JSON 文件。
