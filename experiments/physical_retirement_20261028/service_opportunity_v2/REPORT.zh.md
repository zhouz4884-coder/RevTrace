# 实际服务 pilot：及时执行相同的有效计算

这两轮的机会是让其他合法会话赶上结果仍然有用的时间窗口。当前证据支持这种具体服务作用；不支持“总模型计算减少”或“已通过整场双 P99”。

所有数据来自已完成的 frozen-v2 实际 GPU 服务日志，没有新推理、离线生成替代或期限重置。执行提交为 `1d8c30804a945570429d85d934b3bfcba6171a43`。

## 分母、时钟和可复算材料

两轮、两臂均为同一 16 个来源，完整 offered 音频为 **250.18 秒、4,002,880 个采样点、135 个 offered frontiers**。实际 input ACK 的最终接受总量也为 4,002,880 个采样点，最终认证覆盖率均为 1.0，没有用丢弃或未接受音频缩小分母。

期限始终从 `episode origin + source offset + frontier / 16000` 计算，再加显示 2 秒、认证 8 秒。ACK 在此分析中只用于判断输入何时已真实接受；它不是新的延迟起点。每个 frontier 的原始释放时间均重新检查过。

`OPPORTUNITY_EVIDENCE.json` 保存两轮逐行完整输出、输入字段及输入审计指纹、队列和实际 Consumer 证据，附所有输入文件 SHA256。执行 `python recompute.py` 可重新产生该 JSON。其输入是本目录四个原始 cell 子目录，脚本不导入生产调度器，也不执行模型。

## 一条可定位到实际行的因果链

两轮均只实际取消 session 8 的第 5 个窗口。这一批其他 15 行已经完整完成，而该会话仍继续生成。正常 row-complete 必须继续持有物理 worker，直到整批 drain。

随后第 6 窗口的 16 行，两个 arm 的以下内容均逐项完全相同：原始音频与反馈 prompt、实际 processor/model-input audit（含整个 batch 的 tensor 指纹）、peer 顺序、完整 Z、P、UTF-8 text 和 EOS/token-limit 状态。这里有一个很强的机制控制：服务结果变化可以定位到相同有效计算的执行时序，而不是该批换了更简单输入或更短输出。

| 实际记录 | r0 row-complete → covered | r1 row-complete → covered |
|---|---:|---:|
| 15 个其他会话接受音频且前行完成后，等待下一次实际 enqueue | 0.843–0.859 → 0.093–0.107 s | 0.651–0.666 → 0.0027–0.0178 s |
| 第 6 个 Proposer batch 实际 dispatch，距原 episode origin | 12.889 → 12.144 s | 12.698 → 12.042 s |
| 该批 16 行的 Owner 结果 | 16 obsolete → 16 display | 16 obsolete → 16 display |
| 该批首次实际 Consumer 获得对应前沿 | 等 canonical-display → 由合法 display 获得 | 等 canonical-display → 由合法 display 获得 |

例如 r0 的 session 0：12 秒音频在 **12.0263 s** 已收到 input ACK，前一行在 10.9065 s 已由 Owner 收到，但其下一次 enqueue 到 **12.8690 s** 才发生。covered 中相应输入在 12.0335 s 已接受，实际 enqueue 为 **12.1263 s**。session 0 不是被取消的会话。

基线中，第 6 窗口完整结果赶到时，Authority 已覆盖对应音频，16 行都被正确判为 obsolete。covered 把它们前移后，同样的 16 个完整结果都实际成为合法显示。不能把这一现象简单归结为“少生成了几个 token”。

## EOF 窗口说明为什么尾部可以放大成用户延迟

r0 中 session 0/2/6/10 的短 EOF 第 7 窗口，原显示期限分别为 14.215/14.295/14.455/14.060 s。基线直到约 14.482 s 才重新有调度机会，这四个尚未发出的私有窗口已被 deadline retirement 正确计入，实际用户只能等 Authority，于约 15.87–15.99 s 看到最终前沿。

covered 中四个实际私有 job 在约 13.777–13.783 s 已发出，实际 Consumer 于 14.372–14.431 s 获得其最终前沿。三个仍稍晚于原 2 秒显示期限，不能算全部救回。r1 也重新发出了原本未发出的 session 0/2/10 EOF job；session 6 基线原本有发出，但 covered 也更早服务。逐项结果见 JSON 的 `short_EOF_rows`。

按完整 offered 音频权重重算，r0 新增满足双期限的音频为 20.14 秒，也有 **4.755 秒由通过转为失败**，净增 15.385 秒；r1 新增 17.255 秒，没有相应回退。这保留了负方向结果，而不是只列有改善的会话。

## Authority 与总计算的边界

第 5 批实际 Proposer 模型阶段缩短：r0 为 2.6183→1.7797 s，r1 为 2.4725→1.6870 s。但后续发出了更多原本赶不上期限的合法私有工作，反馈和分批时序也随之改变。两个 worker lane 的模型阶段总和均没有减少。

| 整场实际指标 | r0 row-complete → covered | r1 row-complete → covered |
|---|---:|---:|
| 模型阶段秒数之和（两个 lane，非整场 wall time） | 29.0925 → 29.1476 | 28.6601 → 28.7257 |
| 物理 lease 秒数之和 | 31.8382 → 32.2160 | 31.2126 → 31.6847 |
| all-offered goodput | 10.4423 → 11.1893 | 10.6921 → 11.4868 |
| display P99 | 3.7218 → 2.7529 s | 3.6631 → 2.1300 s |
| commit-view P99 | 3.7218 → 3.9344 s | 3.8578 → 3.8876 s |
| 两板 GPU 能量 | 8673.6 → 8562.2 J | 8639.6 → 8577.6 J |
| 整场双 P99 | false → false | false → false |

Authority 没有被取消，也没有减少必须认证的 135 个音频窗口。r0 的 Authority 模型阶段为 15.0887→15.1448 s；r1 为 14.6048→14.8930 s。两个 arm 的最后实际 drain 都由 Authority lane 决定。其工作占两个 lane 模型阶段总和约一半，谈“完全由 Authority 支配”过强，但认证尾部显然没有由这一次 Proposer 退出解决。

旧 v1 raw 的“17 个 invalidation、1.63565 个 post-invalidation model seconds”也需要这样解读：17 条行记录实际只落在 Proposer 第 5、6 两个物理 batch，批次去重后的占用分别约 0.90162、0.73403 s。第 6 批最早一行失效时，其他行仍可能有用，不能据此把整批剩余时间算成可立即释放。这是已观察占用，不是反事实节省，更不是总服务加速。

## 我的判断

当前可争取的系统贡献是：可信状态推进后，及时停止确实无用的计算，保护其他仍合法计算的服务时效；同时让相同有效计算的进展继续到达实际用户。两轮都出现了输入、完整输出相同但从“整批全部过时”变成“整批全部可用”的现象，这比单独汇报尾部减少更有说明力。

它还没有证明自然 trace 的普遍性、独立新来源的复现、整场双期限通过，或普通 watchdog/父版本取消不如该方法。这些强对照尚未由本报告评价。两轮重跑也不能当成新的独立音频来源。

对于“双时间线 × 分支保留”，这提供了一个有价值的机制假设：资源退出让下一批赶上有用窗口；分支保留决定这些反馈结果能否跨可信 root 推进继续计算；双时间线决定这些结果是否仍成为用户看得见的进展。真正的相互作用仍需 H3 的严格 2×2 独立确认。若只有双时间线就解释全部效果，应缩减组合互补性的主张；若联合设计在保持认证、输入义务与成本边界下稳定改善连续合法进展，即使 Standard 完整组合后同效，也支持组合能力与接口设计的贡献。
