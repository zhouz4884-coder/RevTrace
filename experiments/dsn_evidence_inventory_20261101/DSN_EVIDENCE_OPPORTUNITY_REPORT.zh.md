# RevTrace：跨版本证据检索与 DSN 补强取舍

审阅日期：2026-11-01。审阅对象：当前 DSN v9、旧 TC/FGCS 手稿、用户提供的比较意见，以及本地 RevTrace 研究目录。

**我的结论：确实有值得取回的证据，但最值得补的不是四个历史大数字，而是“为什么这几个判断必须分开，以及这种分开如何改变真实服务”的证据链。** 当前 R×S 主线不应换掉。最有价值的补强，是将它连接到内容选择的真实后果、结果跨进程生命周期、物理资源释放和运行机会分布。

这次是只读证据审阅及其文档交付，没有运行新模型、GPU、TLC/TLAPS、旧结果重计器，也没有修改论文、旧实验或执行源指针。以下历史数字是查阅已有记录所得，不是本轮新实验结果。

## 3. 最值得取回或重新呈现的证据

### P1：把三个判断对应的“不可互相替代”写成可检查的反例

现在已有 EL/AU/SUP 标签和形式状态数，但还可以更清楚地展示它们各自阻断什么、保住什么。建议在方法与评估间用一个紧凑的反例表，替换重复的解释散文：

| 被压缩掉的区别 | 已有见证 | 对论文的增量 |
|---|---|---|
| 当前输入合格，不等于返回内容被原程序选择 | M current-read-set/content-only；或 ASR role-limited coherent return | AU 有真实后果，不只是又一层 checksum。 |
| 当前调用的输入确认，不等于它预测的后继正确 | 旧独立原生 bank 的 20/92 终点被原纠错改写，调用仍合法；有限规格命名控制对应这一点 | 解释为什么保留的是完整原任务，而不是采纳预测。20/92 已在 v9，须增强解释，不能称新漏掉的实验。 |
| 祖先失配，不等于未来完整输入已被反驳 | 原生规格 UNKNOWN→后续收敛的三前沿/四调用控制 | 给朴素整棵子树取消一个具体反例；这是规格控制，不是自然发生率。 |
| producer 无权再发新消息，不等于已拥有结果失效 | 当前 buffer4：真实退出/fence 后两匹配结果继续安装，两失配结果拒绝 | 将保留主线直接连到 DSN fail-stop 语义。 |
| 消息 ACK/行完成，不等于物理槽可复用 | K24 的真实 request→ACK→drain→next dispatch→actual Consumer | 资源生命周期是完整协调的一部分。 |

形式证据的价值在这些区分，而不是把旧 TLAPS、TLC、fuzz 和当前实际转移数堆成一个总 N。相关入口：[原生有限模型](../dsn_native_refinement_20261030/FORMAL_MODEL_RESULTS_v3.zh.md)、[专题审阅 §11](FEEDBACK_CAUSAL_AUDIT.md)。

**创新定位**：我们自己提出并实现的完整组合，不因强正控重现了同等能力而失去原创性。需要证明的是这些对象和边界在递归反馈任务里如何被组织、为什么简单替代会丢失合法服务，以及完整实现如何兑现它；不需要声称每个日志、校验或索引原语都是首次发明。

### P2：取回 M 的真实下游后果，让 AU 的重要性落地

[M_DECISION.md](../legal_progress_20261026/M_DECISION.md)、M_EPISODES.csv 和内容-only 审计给出了比“可能污染后续计算”更明确的结果：

- 8 个任务×2 次重复；当前读集仍合法，干净条件均得到 16/16 正确记忆、14/16 正确后续答案。
- 只替换内容、保留外围格式与 token/EOS 后，OCC 仍安装 16/16 错误记忆，实际后续模型消费，答案变为 0/16。
- 三种受保护方法均保持 16/16 正确记忆、14/16 正确答案；新增可归因的失败为 14/16，涉及 7/8 任务。不能把原来已错的两例算成新增损害。

这能用两三句回答“为什么版本正确仍不足以获得内容选择权”。它不是天然故障频率、LangGraph 漏洞或当前 native fail-stop 定理覆盖的敌手模型；作为有明确干预点的历史因果动机使用。主文选 M 或 ASR role 两者之一，其余放 artifact，避免另开 Agent 泛化主线。

### P3：把当前结果跨 producer 退出的对象身份画清楚

当前源的 buffer4 已经补足早期 36 格中缺失的 complete-buffer 安装见证。可用一个小图贯穿同一 child UID、birth 和 incarnation：完整结果已接收→producer 退出/CUDA 释放→sealed channel 验证/fence→等待实际父输入→同输入安装、异输入拒绝。另一条新到迟消息在 fence 处终止。

这里不是简单地“worker 死了仍能显示缓存”，而是**结果有效性、消息授权和状态安装资格分别判断**。当前四格是定点受控见证，不能推广为任意进程/主机故障覆盖。354 durable /352 原 Owner install /354 Consumer 的差异可用两例 post-sync/pre-install 恢复解释，不能改成 354 次新神经生成。相关入口：[最终 R1 报告](../dsn_strengthening_20261031/FINAL_R1_EXECUTION_REPORT_20261031.zh.md)。

### P4：让物理退出到服务收益的链条可见

[K24](../dsn_joint_retention_exit_20261028/RESULTS_FINDINGS.zh.md) 已有 675 个严格同完整输入/peer-order 对，完整输出相同；同步后继六批的 96 行均被实际 Consumer 使用。当前 v9 已写摘要，主要缺的是表达。

一个可复核的 r1/R1 见证是：请求后 22.196ms ACK，再 13.359ms drain；下一批同 16 行开算提前约 577ms，实际首次消费提前 456.5–573.0ms。其中 6 行从 miss 变 hit，10 行本来就 hit。图中不能把 16 行都涂成新增成功。这一个见证也不是典型取消延迟；全体 91 次 cancel 的 request→ACK、ACK→drain 上界分别可到 0.645s、1.643s。

这一轮还实际包含 242 个完整输入兼容、116 个不兼容的跨 Canonical 正常 decode：该保留和该退出的工作确实共存。不过正常计算最长 1.292s，不能称已证明超长合法任务不被 watchdog 误杀。R×K 服务交互跨相位符号混合，没有稳定全场节能。退出应作为执行支撑，不能硬加一个普遍协同主贡献。

## 4. 还有价值，但应控制主文位置的证据

### 恢复三时钟：恢复旧服务可以快很多，恢复新推理仍然慢

[trusted renderer 四臂冷恢复](../trusted_render_dependency_20261028/RECOVERY_RESULTS.md)：RevTrace 旧事实全部实际可见从 15.592s 降至 2.471s；完整 Standard 从 15.807s 降至 2.515s。仍逐事实重新 Render 和核对绑定，独立重建 185 行、87 个 batch 输入、56 个 durable text 绑定，不是直接信任缓存文本。

首个新事实和清偿原输入债务仍约 19–22s，并略退；没有全场 D2/C8 或能耗胜利。四个单次开发试验，历史 core 合同，与当前 native 故障 bank 分开。这是有信息量的系统工程与恢复对象设计：恢复读取既有事实的可信依赖不必等同于恢复完整推理栈。优先放 artifact 的三事件恢复图；正文若有空间写两句，不能抢占当前协调新意。

### 同样音频，完整输入会双向改变计算成本

[8 个 paid batch 控制](../context_recovery_20261028/PAID_INPUT_RESULT.md)：一个 case 更新输入后 prompt 反而变短，但新 token 从 7 增至 21，lease 变长；另一个 case 从 20 降至 12、批次能耗下降。均完整 EOS，不是 token cap。它说明反馈不是一个仅改标签的版本位，也不能假定更新输入必定便宜。是两例×两输入×两重复的付费算子，不是部署调度收益。

### 少做逻辑行，不必然少付物理计算

[物理批次账本](../final_evidence_integration_20261028/PAID_WORK_RESULTS.md)：一次旧开发对照中，102→67 Private rows，14→17 batches，GPU0 model wall 20.692→20.854s。181 个 physical batch 全收费。这个反例适合解释为什么协议按 batch drain/真实付费工作判断，不能以 token 或丢弃行数代替节能。它不是当前 R×S 的性能估计。

### 固定相同 Authority 结果，只改安装时序，未来成本仍改变

V6 C 的 48/48 目标 Authority 完整输入、batch、Z/P/text 相同。延迟安装 1.5s 使未来 Private lease 每 run 多约 5.8–6.3s；0.75s 若没有跨越真实 dispatch 的冻结时刻则不触发同样效应。可用来解释为何研究相对推进与冻结时刻，比扫描一个固定 rho 更接近机制。属于旧合同的受控因果见证，不能替代当前服务窗口实测。入口见 PROTOCOL_COST_AUDIT.md §8。

### 合法的细粒度复用对象，不一定经济

Stage handoff 的真实单源服务 pilot 与 encoder carrier 组件测试，不只是“失败实验目录”：更细的 ASR/E 对象存在合法复用，但等待、捕获、传递和校验税可能吞掉机会。E 在 4/14 使用率下完整 eager 账本余量为 −0.305s（组件计算，不是部署慢 305ms）。这支持为什么最终选择完整原调用作为保留对象。用三行设计取舍表或 artifact，而不是把它们包装成未完成的新缓存算法。

### 保存历史的对象应是未来依赖闭包

证据 retirement 的 24 个 CPU 构造场景中，激进 endpoint contraction 丢掉 18 个合法迟到进展；完整活跃根闭包和普通强修复都 24/24 等价。原 formal 也有 latest-safe 安全却不保留最大合法进展的反例。适合给控制历史保留条件一句依据；不是 GPU 长期存储胜利，也不是总内存有界的证明。

## 5. 真正尚缺的内容：下一次投入应对准什么

### 第一优先：当前完整实现的成本，而非旧 101 μs

CK5 已有同输入 early-k0/k1 的 8 对全链对照：goodput 变化约 −0.13% 至 −0.42%、WER 不变；display P99 增 0.041–0.404s。这比孤立旧提交微基准更有用，但 composed kernel/Consumer/原生调用之后有变化，仍不能充当 v9 成本。

已有日志字段可帮助定位：R 的 proof_host_wall_seconds、kernel 的 thread CPU、controller CPU、input fsync 等。然而这些计时的范围不同，kernel timer 不含 lock wait、部分 hashing/Consumer；分组 WAL 的同一 elapsed 不能按每个 commit 重复相加。把现有字段相加不会自动得到完整成本。

若下一轮增加实验，首选小型同输入、当前冻结源的完整协调成本分解：分别记录冻结输入检查、依赖支持检查、消息/对象身份、选择与安装、Consumer 应用、WAL 同步，计重叠和等待；搭配一次正常端到端对照。保留所有安全谓词，并明确无检查控制仅作 CPU 归因、不能输出不合法服务。避免再做一个只测空 fixture 的漂亮微秒数。需要按项目合同单独冻结、登记、执行；本轮没有执行它。

### 最值得重新打开的研究机会：历史最大合法进展，是否能恢复持续覆盖

这项不是把旧失败换个名字。旧 S 分析的反面结论是“没有新增首次 D2 信用”；当前论文则明确区分首次交付与持续可用性。两者目标不同，需要重新判断，而不能被旧 NO-GO 标签直接带走。

对照实现后，二者的能力也有真实差别：v9 主要重验当前 tentative view，在它不兼容时清空或回到 Canonical；并没有在所有已登记历史 nodes 中重新选最大合法 tip。旧 S 已实现 Consumer-registered 最大合法进展查询。因此“保住眼前仍合法的 view”和“从历史找回另一个仍合法的 view”是不同的服务完整性性质，不能因为普通多版本索引也能实现就否定它在本系统中的价值。

目前支持的是：N5 三条真实运行有 14 个已发布、权限仍合法的历史选择改善 cut；六策略经实际 FIFO 的 CPU 重应用和原 kernel 检查，普通完整索引与扫描同效。**14 是时点，不是 14 段独立空窗，更不是已测的用户收益。** 已发布/Consumer 登记也不自动等于此前已合法显示：接收时不兼容的节点可能已存入 nodes。新分析须分开恢复曾显示覆盖、新 root 下变得可用的历史节点、当前 view 持续保留。它们不能直接提供持续时间、自然频率或当前原生端到端收益。

还发现旧 S0 的首次 D2 枚举只检查完整 fine=2s 网格，部分 partial-EOS cut 的 deadlines 为空。这不推翻其原口径结论，但限制了“任何新信用都没有”的外推；新分析必须使用当前 all-offered、包含 EOS 尾段的分母，不能默认两者一致。

建议先做一次有界、冻结的原轨迹持续覆盖分析，暂不开新模型矩阵：

1. 从实际发布/Consumer 应用时钟重建每个 root 与撤销时刻，所有结果保持原发布权限、generation 和完整依赖；不让未发布 host 结果提前可用。
2. 对同一输入/事件流比较 current-view retention、普通完整历史扫描/索引，测完整区间缺失的持续时间和 audio-time unavailable area；必要修订与不必要空窗分开，首次交付信用不重复计算。
3. 查明 14 个 cut 是同一个机会的重复观察，还是存在非零完整区间；同时统计全部 root 更新/全部 offered 音频，包含 partial EOS，并保留完整文本支持。
4. 若只有瞬时较大 frontier、没有持续可见收益，或历史已被合法撤销，终止这条服务增量。若有稳定非零窗口，再在当前原生完整合同接入最简单的历史查询，同输入 fresh-process 配对，测真实 Consumer、质量、资源与持久化代价。

本地 RAW_EVIDENCE 包确有 18 份旧 CPU 重放 Consumer 记录，但其 observed_perf 是快速重放产生的新时钟，不能当原服务窗口。需要按 S0_N5_SCAN_v2 中三个 attempt 的 trace_identity，从原位置取回 hash 对应的 consumer/events 及必要 worker/config/session 记录。原事件流 CPU 重应用也只能建立离线机会，不是新的部署速度。

即使强普通索引同效，系统贡献仍可定位为“跨修订服务完整性及其最小实现”，不需要再发明复杂索引。这是本次比补回旧 fuzz/加速比更值得保留的潜在研究方向；本轮只完成差异诊断，没有完成上述新分析或其收益验证。细节见 PROTOCOL_COST_AUDIT.md 的 S14 补充。

### 容量扩展：只有要主张部署 scale-out 时才测完整合同的副本扩展

固定 source、音频、到达、完整输出预算、Consumer/WAL；比较一对与两对 worker（确有四卡资源时），一个欠载和一个压力点、fresh-process 配对重复。可证伪问题是：增加资源改善首次及时性时，协调机会是保留还是自然收敛？这比再追 50xRT 有价值。旧 8 卡结果不能替代它；不主张当前 scale-out 则不必为补表格而开大矩阵。

### 不继续优先的方向

继续横向扩模型追自然 flip、大规模复刻同类 fuzz、增加取消理由、靠新 admission controller 抢额外胜点，当前边际价值低。两客户端 admission 固定门已经 NO-GO；不能拿旧 selective/risk-limited c12 正点绕过。旧 S 则应按上面的新服务目标单独评估，不能与这些低收益方向一并关闭，也不把未测的持续服务收益当结果。

## 6. 我会怎样选择论文材料

全文仍只保留一个主信息：**可信反馈推进时，完整调用的输入资格、内容选择权和整视图支持可能分别变化；把它们联合协调，才能既允许必要纠正，又不无谓丢掉仍合法的进展。** 故障和物理退出是同一对象生命周期的执行完成，不再增加三条平行故事。

主文优先用：现有真实案例→三个独立义务及反例→R×S 交互→原生完整调用→结果跨退出→工作区间及代价。补回 M 只占动机短段；将当前 buffer4 身份链和 K24 兑现链画得更清楚；用分层表替换池化数字的重复解释。若需要腾空间，先移开发史和重复免责声明，而不是加入四张历史大胜表挤掉当前方法。

Artifact 保留历史 fuzz/微基准/容量账本、renderer 三时钟、paid batch 和细对象选择。所有旧数字按真实源和合同单列，不合并为当前整体安全、质量、服务或自然发生率。

这不是说已经达到录用强度上限。现有材料足以继续提升问题重要性、机制辨识度和系统完整性；最明确的实测缺口是当前完整成本归因。是否值得新的模型/容量活动，应由它能否回答一个新问题决定，不能只由尚有 GPU 时间决定。
