rho=1 runtime beyond fixed generation/verification and simple cost/readiness
switching, when all methods share row delivery, FP16 GPU0, FP32 GPU1, D1,
Consumer and durable WAL? The scheduler predicts cost, never certifies content.

2. Calibrate only from completed development-source 72+120-cell histories;

3. Implement a runnable bounded CES and safety/interleaving tests, then fresh

4. Freeze model/config, source, independently selected audio, policy parameters,

## Non-negotiable execution rules

- Direct FP32 generation and strict full-token/stop/budget verification with a
  real complete FP32 fallback are the only Authority operations.
- Homogeneous physical batches; a physical lease ends only at BatchDrained.
  Candidate readiness is a scheduling input, never a waiver of verification.
- Every installation uses the original Parent/Frontier/Contract, A/B/C/D, D1
  trusted render and WAL. Mode choice is declared by the frozen runtime and
  bound to the job/row receipt. Failed fallback yields no installation.
- Fault plans name frozen session/audio frontiers, not scheduler-specific job
  numbers. The fault injector and decision feature extraction are separate.
- Same ready/executor capabilities, hardware and budgets for Fine, Strict,
  Readiness/Birth, Cost-only, full CES and Standard Safe Async.
- Costs include rejected verification, obsolete private work, all fallback,
  CPU/IPC, complete physical drain, WAL/fsync and Consumer application.
  Every requested audio frontier remains in the denominator, including failures.

## Contribution decision

GO requires independent Mixed-workload repeated statistical evidence against
the best fixed legal method *and* Cost-only and the simple gate, in certified
Goodput or energy at supported comparable quality, without new violations.
Otherwise retain all negatives and state which requirement failed. Shared row
executor wins are not a CES contribution. Pilot numbers are not formal results.

Formal sample sizes and policy parameters will be frozen after bounded pilots,
not selected using validation outcomes. Deadline reporting will include the
primary 2s Display / 8s Commit pair, complete latency distributions and all
incomplete requests. Alternative deadline grids are explicitly secondary.
