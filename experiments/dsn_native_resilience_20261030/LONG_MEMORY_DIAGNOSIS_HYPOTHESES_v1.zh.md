# 长参考显存问题：假设与判别控制（尚未形成最终修复结论）

2026-10-30。原两条合成长流与原C/U保持。9492长参考的连续原程序路径在S0770第95边（47.0→47.5s）OOM；最初参考仅保存PROGRESS94和边界遥测，没有持久化94个完整cut，不能将其称为94步等价证据。随后独立诊断driver逐边保存完整原轨迹，并在两个fresh运行复现相同失败入口。该完整入口的两次原`NativeBridge.full_step`调用均成功并得到相同完整end。

## H1：声明的cut遗漏影响后继的状态

预测：从捕获的同一完整入口恢复后，原step无法复现连续原程序的合法结果，或同输入重复不稳定。现有两次单边恢复成功且结束一致，尚未支持H1作为此次OOM的原因。但这不等于整个875边的状态充分性已经通过；仍需完整连续/恢复对照。

## H2：参考调用器保留非语义GPU诊断对象

代码依据：`continuous_transitions`将`ids,g = engine.infer(...)`保留在generator locals中，yield后进入下一轮infer前，旧`g`仍可存活。钉住的作者infer将GPU `Logits`对象放进`generation['logits_starting']`及生成进度；这些对象不属于闭合反馈cut。相比之下，`NativeBridge.step`返回只提取的C/IDs/cut后，其局部g可自然释放。

可证伪控制：统计g可达GPU存储（去重，不把共享权重反复计数）、释放前后allocated；只提取原C/IDs与完整cut后释放非语义诊断对象，再以相同输入连续运行到第96边。原连续前缀、失败入口及两次单边95输出都须严格比对。不能只以“没OOM”当作任务保持，也不能删除真正影响后继输入的状态。

## H3：缓存分配布局或碎片造成临界失败

OOM报告显示一次约912MiB申请，物理空闲约817MiB，torch还有约2.58GiB reserved-but-unallocated。它给出分配布局机会，但不直接证明全部原因是碎片。[PyTorch 2.9官方说明](https://docs.pytorch.org/docs/2.9/notes/cuda.html)明确将`expandable_segments`列为实验选项，用于缓解变化大小分配形成的不可复用碎片。

如需测试该选项，应作为固定环境对照记录在配置/环境中，维持FP32、原模型、原C/U与数据，完整前缀一致后才能采用；两正式策略必须使用同一最终环境。优先辨别H2，避免用分配器掩盖活跃诊断对象的持有。

本轮诊断属于参考/模型资源机制控制，不是在线服务收益、协议状态错误或长期内存有界的证明。首次失败、同输入重复、legal oracle及所有新driver源码身份分别保留，最终两条完整输入不因该失败替换或缩短。
