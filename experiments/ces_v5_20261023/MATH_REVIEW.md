# V5 数学与动作空间审计

本文件记录 CPU 实现与可复现的调度模型反例。证据等级是 **确定性 CPU scheduling fixture**。所有服务时间均为明示的构造输入，未生成新的 GPU 性能结果，未将不同真实运行的 Token、投影或轨迹拼接为动态执行。正文与历史冻结结果未修改。

## 1. 结论及最小修正次序

V5 的实际 Consumer Display 观测和整批风险成本是必要修正，但它们本身不保证调度能力增加。此次实现审计找到了三个需要先处理的问题：

1. 将 Commit 期限违约置于字典序首位，可以牺牲真正的双期限 Goodput。状态准入安全是硬约束；Commit SLO 是性能目标。两者不能混为一种不可牺牲的优先级。
2. `E[新增按时音频]/E[当前共同 cut 完成时间]` 只是局部比率目标，不等于整 run 的有限时域 Goodput，也不等于 `E[音频/时间]`。
3. 验证/生成各最多一个批次的前缀枚举会漏掉合法且有价值的 G/G、V/V 拆批及零即时收益 Parent 的后续解锁价值。没有候选时，原动作集几乎退化为唯一的全量 Generation；此时改善目标函数也不能改变执行。

建议优先完成共享的有限拆批搜索、真实逐行完成分布和正确的残余收益目标，再考虑更长的因果规划。无需先加入 RL。每次动作集合扩展都应同样提供给风险成本对照，才能区分“能选择更多动作”和“选得更好”。

初版 policy 的 source-level 细节：保留旧 Cost-only 首动作后再用 Generation 补齐剩余集，可能偶然产生一个 G/G 分割。因此准确描述是 **缺少系统性的同构拆批搜索**，不能绝对声称源码完全没有 G/G。

## 2. 双期限信用的正确定义

对释放时间 `r_i`、音频权重 `a_i` 的前沿，固定 `dD_i=r_i+2`、`dC_i=r_i+8`。实际 Consumer 第一次合法观察时间为 `D_i`，耐久准入时间为 `C_i`：

`q_i = a_i * 1(D_i <= dD_i) * 1(C_i <= dC_i)`。

Display 已按时完成且 Commit 未完成，仍有完整的残余 Commit 信用。Display 已错过期限，当前前沿自身的双期限信用为零；它仍可能是后续合法 Parent 的必要前驱，不得删除、遗漏分母或永远饿死。迟到的 Canonical 发布不能回填过去的 Display 成功。

这些规则保持现有“第一次合法观察”口径。若早显示随后回撤，首次观察信用与回撤指标必须同时报告；不能通过延迟已就绪的合法提交来积累旧 Provisional 显示信用。

## 3. Commit 优先能够降低真实双期限信用

在 `now=0`，考虑完全符合 2 秒 Display / 8 秒 Commit 的两个任务：

| 任务 | 释放 | Display deadline | Commit deadline | 已有显示状态 | 合法证据工作 |
|---|---:|---:|---:|---|---:|
| A | -6.5 | -4.5 | 1.5 | Display 已失效 | G(A)=1.4 s |
| B | -1.5 | 0.5 | 6.5 | 尚可按时显示 | V(B)=0.2 s，通过 |

两个完整计划处理完全相同的任务，总墙钟都为 1.6 s：

- `G(A) -> V(B)`：两个 Commit 都按时，但 B 在 1.6 s 才显示；双期限音频为 0。
- `V(B) -> G(A)`：B 在 0.2 s 完成并取得 2 秒信用；A 的 Commit 晚 0.1 s；双期限音频为 2 秒。

旧的“先最小化 Commit-late audio，再优化双期限信用”规则选第一条。第二条没有放松任何 Parent、Frontier、Contract、Token、Trusted Render 或 WAL 条件，改变的是服务质量权衡。应将实际双期限收益作为首要性能目标，Commit P99/违约作为同时报告的约束或次级目标，而不是称之为准入安全要求。

`test_commit_priority_counterexample_matches_fixed_2s_8s_contract` 使用上述实际期限关系；Oracle 另有 1.2 s 的简化同构例。二者都只是构造性机制反例，不是某次 GPU 运行的反事实收益。

## 4. 三个比率目标并不等价

### 4.1 局部比率与有限 run 比率

已经经历 `T0=10 s`、累计信用 `Q0=0`，两个完成同一剩余 cut 的计划：

- A 增加 2 秒信用，耗时 1 秒；局部比率 2。
- B 增加 3 秒信用，耗时 2 秒；局部比率 1.5。

局部比率选 A，但整个有限前缀的比率分别为 `2/11≈0.182` 与 `3/12=0.25`，应选 B。

确切代数关系是：

`(Q0+deltaQ)/(T0+deltaT) > Q0/T0`

当 `T0>0` 时等价于：

`deltaQ - (Q0/T0)*deltaT > 0`。

它说明当前 Goodput 可提供有单位的时间价格，不能据此宣称任意短视的平均收益优化都是全局最优。未来到达、未知 Parent、队列影响和截断视野仍然存在。

### 4.2 比率的期望与期望的比率

计划 A 有两个等概率结局 `(Q,T)=(2,1)`、`(8,10)`：

- `E[Q]/E[T]=5/5.5≈0.909`；
- `E[Q/T]=(2+0.8)/2=1.4`。

计划 B 恒为 `(1,1)`，两个指标都是 1。两个期望准则对 A/B 的排序相反。

因此不能把期望信用除以期望 lease 称为“期望 Goodput 的精确优化”。它是可实现的局部启发式。若下一版采用场景 rollout，可以直接计算每个场景下 `(已观察Q+预测deltaQ)/(已观察T+预测共同cut墙钟)` 后再平均，明确这仍只是该有限 cut 的预测目标。

### 4.3 半计划不能与完整计划比较

只执行一小批紧急 Verify 的信用/耗时通常高于完整 Generation，但剩余任务仍然欠付。计划比较必须完成同一已声明 cut；或为所有剩余任务加入统一、合法且实际计费的完成策略。Oracle 强制每个任务恰好完成一次，不能仅靠省略难任务得到高分。

## 5. 同构拆批是一个实际动作增量

模型反例 G/G：两个任务中 A 的 Display deadline 为 0.5 s，B 已按时显示。单个二行 G 批需要 1 s；两个单行 G 各需 0.2 s。全批获得 2 秒信用，G(A)→G(B) 获得 4 秒，且两条计划均处理全部工作。

模型反例 V/V：A 的 Display deadline 为 0.5 s，B 已按时显示；单批 V(A,B) 耗时 0.7 s，分为 V(A)=0.1 s、V(B)=0.6 s。总成本相同，拆批使 A 及时显示，信用由 2 秒变为 4 秒。这里没有假设免费 Fallback 或提前释放仍占用的 Worker。

上述成本可能在真实数据中不成立，必须由实际合法输入与 Batch 形状实测验证。它们证明的是动作枚举可以存在遗漏，不证明拆批在 RTX3090 上必然获益。

GPU0 同样需要检查实际动作集合。在最多 16 个单飞 Session 且 batch limit=16 时，仅把全部 ready rows 重新排序通常不会改变被选集合；对尚未过期的统一 2 秒前沿，EDF 还可能与 FIFO 相同。此时所谓 joint 调度主要改变行顺序，不能直接声称获得新的调度自由度。应显式测试有限子批、合法等待和其完整成本，且所有对照共享这些能力。

## 6. Parent 解锁具有互补性

构造两个 Session 的链 `A->B`、`C->D`，另有独立 E。每个前沿音频权重均为 2 秒：

- A/C 的 Display deadline 为 -0.1 s；B/D 为 1.9 s，满足同 Session 相隔 2 秒。
- E 的 Display deadline 为 0.6 s。
- 所有音频已释放（release=Display deadline-2），Commit deadline=Display deadline+6。
- 合法 Parent 批 G(A,C) 耗时 0.8 s；其后子任务批 G(B,D) 耗时 0.8 s；G(E) 耗时 0.6 s。

只看立即正信用会先执行 E，在 0.6 s 得到 2 秒信用，再做 Parent 批、Child 批；B/D 在 2.2 s 完成，均失约。

完整合法模型中的最优顺序为 Parent 批→Child 批→E；B/D 在 1.6 s 完成，获得 4 秒信用。两个计划都在 2.2 s 完成全部任务。Parent 批即时信用为零，但它与后续动作组合产生正信用，因此收益不是简单可分解的任务密度；不能无条件援引普通 greedy density 的近似最优保证。

这只是已声明 transition outcome/cost 的结构模型。真实执行中的 Child Parent 要等实际 Canonical 结果产生后才能构造，不能提前把历史 Z 改挂新 Parent。当前在线原型没有模拟未知 Parent 的模型输出，因此也不能声称它已经实现该解锁优化。

## 7. CPU 精确有限动作 Oracle

`cpu_planning_oracle.py` 对 1–8 个任务、明示的同构动作及确定性成本枚举完整合法调度：

- 动作只能 G 或 V；无就绪候选的 V 不可用；
- Parent 依赖必须在派发前完成，禁止同批 Parent/Child；
- Row-complete 可以早于 lease 结束；下一次派发仍等前批排空；
- 所有任务进入共同完成 cut；
- 可选目标为完整 cut 的比率，或用于复现错误的 Commit-first 比率；
- 可关闭 Pareto pruning，与完整枚举逐项核对。

状态是已完成集合 `M` 的标签 `(time, credit, commit_late_audio)`。在本模型的固定成本、固定合法转移、固定候选可用性条件下，若标签 L1 的时间不晚、信用不少、Commit-late audio 不多，则其任意相同后续计划均不劣于 L2，可以剪枝。每个动作只增加完成集合，因此完成集合上的动态规划是无环的。

该支配关系不自动适用于真实 RevTrace：如果同一已完成集合具有不同 Canonical Parent、Private 链、物理输入形状、剩余 GPU lease 或不同候选状态，就不能仅凭 `(M,time,credit)` 合并。真实 rollout 的状态键至少必须保存影响合法性与后续成本的实际身份。

`test_cpu_planning_oracle.py` 的 15 项测试通过，其中包括小模型 Pareto 与完整枚举相同、零信用任务不丢、早行返回不释放 lease、同批 Parent/Child 拒绝、未就绪候选拒绝，以及上述反例。

运行方式：

```powershell
cd D:\VLA_QWEN\RevTrace\experiments\ces_v5_20261023
python -m pytest test_cpu_planning_oracle.py -q
python cpu_planning_oracle.py
```

“精确”仅指该有限确定性 CPU 模型的声明动作集合。它不代表真实 GPU、未知未来输入、未知 Token/投影、随机尾延迟或全服务历史的最优解。

## 8. 更高性价比的下一版搜索

建议依次测试：

1. 同一共同 cut 下比较全 G、全可行 V+G 补齐，以及按紧迫期限/预测短行/剩余音频信用的有限同构拆批；额外 model invocation 与完整 lease 计入双方。
2. 真实 row completion 使用 ECDF 或保留批内行分布；不要把平均行完成比例放入 deadline 指示函数。`1(E[T]<=d)` 与 `E[1(T<=d)]` 不等。
3. 用小 `n<=6` 的完整模型 Oracle 检查有限枚举遗漏了多少预测价值，再决定是否扩大动作集合。Oracle 本身不作为服务测量。
4. 对确实存在 Parent 解锁机会的状态再增加一层有界 rollout；只有真实已观察的 Parent/Private 身份可被执行。未知结果可在预测层携带不确定性，不能在执行层当作真实状态。
5. 使用共同的 model/calibration、共同动作预算、共同早返回能力进行 Cost-only、单目标门控与完整策略对照。误预测只影响性能选择，不能改变任何准入谓词。

本轮结论是 **GO：修正局部目标与有限动作搜索并做 CPU 反例验证；PENDING：真实 GPU 性能优势**。仅用这些 CPU 构造数值不能宣称已提升 Goodput、降低能耗或建立新的 DSN 性能贡献。
