# 资源账与运行哨兵：预先固定的解释规则

2026-11-11。补充五臂实验合同。这里规定后续审计方法，不把外部重算的数字预先认定为新实验结果。

## 三种时间不能混用

1. **完整调用占用：** worker实际接手至实际终结的wall时间，按完整job身份绑定；可能含CPU、ASR、纠错、同步、缓存清理、传输等。它是worker占用秒，不能仅凭区间称为GPU活跃秒。
2. **实际推理区间：** 原实现计时器所覆盖的`engine.infer`及其中同步/回调时间。先审源码定义，缺失字段保持missing，不默认成0；只有存在逐阶段实测时，才分别给ASR、prefill、decode或C/U成本。
3. **确认前已投入工作：** 同一个job的实际执行区间与实际父结果可用/Owner验证/合法晋升时刻前区间的交集。分别记录这些时间边界；不能拿整次完成成本替代晋升前已完成的成本。

跨两个worker的占用秒可相加，但不等于两板能量或服务wall时间。推理区间与同一job的占用区间嵌套，不重复相加。重叠时间不直接命名为“节省完成延迟”；只有同输入、合法策略、实际重新调度的配对运行才能支持因果服务收益。

## 逐job闭合

使用`cell/source_id/job_id/worker_incarnation/dispatch_epoch`及完整输入绑定，而不是跨cell只按`j000016`相连。每次实际派发恰好有一种当前物理状态：在飞、完整结果就绪未处理、已安装、完整结果被拒、检查点提前退出、生命周期/故障终结。采用原实现真实状态细分并记录映射，不能用未见记录补0。

晋升是状态转移上的注释，不能再当一个互斥终结类别相加。静态无故障、全部物理drain完成且所有receipt处理完后，才可能化简为`dispatch = install + abandoned + discarded`；若仍有ready/inflight、故障或其他终结，必须保留这些项。

## 必须失败与必须诊断分开

**完整性失败：** 身份不匹配、派发漏账或重复终结、未经原选择程序提交、SUP非法视图被安装、UIR发出禁止的提前skip提示、成功完整晋升却缺少真实模型执行记录。完整性失败保留原输出，修复需要新的冻结版本。

**调度与机制诊断：** Ready-only完整receipt复用为0、重复间占用差超过2%、early/late拒绝比例改变、策略之间某些指标相同。这些均保留在结果中，不能直接判无效、删掉或反复重跑直到变好。

Ready-only复用为0时，检查所有实际install边界的ready-bank与在飞状态、receipt入队/出队顺序、首次显示和重新派发。只有完整可观察行为一致或可证明的策略等价，才能判退化为Conservative。没有ready复用机会本身也是该冻结workload的机制结果。

重复间资源差先分到job数、各阶段成本、物理drain、page-cache/加载状态与外部GPU拥有者，再决定是否需要新的具名控制；差异不是污染的自动证明。所有原重复保留，不以2%作为成绩筛选阈值。

## 对两个late拒绝的改进判据

对每个late结果，依次绑定：子job合法before-C检查点、父job原始模型结束、父receipt可用、实际父安装、失配证明形成、提示发送/接收与子job物理结束。只有证明在原合法检查点之前已可获得，才能归因为“提示发晚了”的可修实现损失。

如果父结果在原检查点之后才产生，不能把未来信息提前；新的后置before-C复查、等待或C中途退出需要独立机制、成本和原任务等价证据。ASR观察的produced_perf只是原检查点之后的上界，不是精确C入口；它不排除另加一次低成本复查的可能性。safe UIR对照保留这个问题的真实资源后果，不预设它必然导致非法提交或连续性下降。
